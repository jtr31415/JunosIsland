## PB-058 — the album opened collections that have no animals built

### What was wrong

`unlock.ts` drew four collections at random from a 21-row roster. Six of those
rows have models built. The other fifteen had none at all, so a draw that landed
on `ocean` handed a five-year-old sixteen empty frames and called it an album.

The card said the fix was one line — put the unbuilt ids in `HELD_BACK`. It was
two, and the second one is the half the card could not see.

### The six that are real, and how that was established

Not taken from the card. Derived from `shippedIn()`
(`src/island/species/registry.ts:144`), which filters `SHIPPED_SPECIES` — the
frozen 24 plus the collections phase 2 and phase 3 actually built — by
collection id. `shippedIn(id).length === 0` is exactly "nothing here can be
drawn".

| collection | shipped | roster |
|---|---|---|
| `base` | 24 | 24 |
| `garden` | 14 | 14 |
| `woodland` | 16 | 16 |
| `farm` | 16 | 16 |
| `home-pets` | 14 | 16 |
| `africa` | 13 | 16 |
| the other 15 | 0 | 14–16 each |

The card's list of six was still correct at the time of the run. It was checked
rather than trusted, and it is now checked on every test run — see the tripwire.

### Change 1 — the holding pen has two halves now

`src/island/species/unlock.ts:66-152`. `HELD_BACK` was three ids and its own doc
said it was "meant to shrink". It is now the union of two lists that shrink for
two entirely different reasons, and separating them is the point:

- `HELD_BACK_BY_JOE` — `legendary`, `dinosaurs`, `prehistoric`. Joe's judgement,
  from JT-027: *"hold legendary, dinosaurs and prehistoric for now"*. Shrinks
  when he says so.
- `NOT_BUILT_YET` — the other twelve. Not judgement, arithmetic. Shrinks when a
  modeller ships a collection.
- `HELD_BACK` — the deduplicated union. The single call site
  (`unlock.ts`, inside `candidates`) is unchanged, and so is every importer.

`NOT_BUILT_YET` is twelve hand-written strings rather than a call to
`shippedIn()` because **`unlock.ts` is pure and must stay that way** — its own
header says "no three.js", and importing `registry.ts` reaches three.js through
`collections/garden.ts` → `parts/assembled` → `parts/texture.ts`. So the
derivation is performed in the test instead, where imports are free.

### The tripwire, which is how the list cannot rot

`tests/island/species-unlock.test.ts`, describe block *"the hold on unbuilt
collections is derived from the registry, not remembered"*. Three assertions,
all derived from `shippedIn()` at run time:

1. every collection with zero shipped species is in `HELD_BACK`, and the failure
   message says how many empty frames a child would see;
2. every id in `NOT_BUILT_YET` still has zero shipped species — **so the day
   someone commits the first ocean species this goes red and names `ocean` and
   says to take it out of the list**;
3. the union is exactly the unbuilt set plus Joe's three, and nothing else.

Nobody has to remember `NOT_BUILT_YET` exists. That is the whole design.

### Change 2 — the prune, which is the half the card could not see

`src/island/species/opened.ts`, step 0 of `advance`.

Adding ids to `HELD_BACK` only stops **future** draws. `HELD_BACK` is consulted
in `candidates()` and nowhere else. A save written before this run already has
up to three empty collections open — and they are **wedged there permanently**:

- `completion()` divides owned by the **roster** member count (16), never by the
  shipped count (0), so an unbuilt collection can never reach 100%;
- never complete means never stops being ACTIVE (`unlock.ts`, `activeIds`);
- so it occupies one of the four `MAX_ACTIVE` slots forever, and rule 1 says only
  a completion releases a slot;
- so **she never gets a new album again**. On a live save that is three of her
  four slots dead.

So `advance` now drops from `open` any id that is (a) in `HELD_BACK` **and**
(b) one she owns nothing from.

**The (b) guard is brief §19 and is not an optimisation.** For a collection with
no shipped species (b) is always true — no model, no pet, no count — so on
today's data (a) alone would do identical work. The guard is there because the
proof rots: `HELD_BACK` is a union, and Joe's half of it is not about models.
The day he releases `legendary`, a child may already have it open and half
collected, and an (a)-only prune would take her unicorns off the shelf. With (b)
the rule is lossless **by construction** rather than by an argument about what
happens to be true this week.

`base` is never pruned (spelled out, though (a) already excludes it).
`lastOpened` is left alone even when it names something pruned — `RELATED_GROUP`
is total, so the relatedness rule still resolves, and it stays an honest record.
`advance` is still idempotent: prune, refill from the five-strong pool, and the
second call finds nothing to prune. There is a test for that.

### The §19 test uses real data, not a mock

`animal-unicorn` is a genuine `legendary` member in `roster.ts`, and
`SPECIES_COLLECTION` is built from `COLLECTIONS[].members` regardless of what
shipped — so `ownedByCollection(['animal-unicorn'])` really returns
`{legendary: 1}`. The test asserts `legendary` survives the prune. No stub, no
fake roster. This matters: HANDOFF §5 is four dead features that shipped because
a mock was asserted.

### The draw cannot starve or deadlock — checked, and covered

This was the real risk of growing a list sized for three into a list of fifteen.
It does not, and the reasons are structural rather than lucky:

- `draw()` returns `null` when the pool is empty (`unlock.ts`, `pool.length === 0`).
- `fillToCap` is bounded by `room-- > 0` where `room` is the pool size, and every
  drawn id is added to `open` which `candidates` excludes — so the pool strictly
  shrinks. It terminates by construction and returns **fewer** rather than
  looping.
- A fresh island: `base` plus three drawn = four active, from a pool of five. Two
  are held in reserve for the only two completions the cadence can still reward.
- The relatedness fallback (`unlock.ts`, "THE FALLBACK, AND IT IS DELIBERATE")
  still prefers a related collection to nothing, so a shrunken pool cannot make
  the presentation rule strand a child.

Covered by the describe block *"the draw can neither starve nor deadlock on the
pool PB-058 leaves it"*, including the hostile case where every buildable id is
already open.

### Tests that changed, and why each one had to

- *"holds exactly three back"* — hard-coded the three. Split into the dials it
  still proves plus the derived tripwire above.
- *"FALLS BACK to a related collection rather than returning null"* — staged its
  pool from three Red List tiers, which are now held back, so `candidates` came
  back empty and the test proved nothing. Restaged on `temperate`
  (`garden`/`woodland`), which is reachable today.
- *"never opens two Red List tiers back to back"* — became **vacuous**: the tiers
  can no longer open at all, so the loop body never ran and the test passed by
  doing nothing. Replaced with the honest statement of what is now true.
- *"spreads across the pool as the seed changes"* — asserted `seen.size > 5`
  against a post-relatedness pool that is now 3. Restated against `candidates()`
  itself (every candidate is reached, nothing outside it ever is) so it survives
  the pool changing size again rather than needing a new magic number.
- `opened.test.ts` *"draws a different four for different children"* did **not**
  break, but the property is genuinely weaker now — three from five is ten
  combinations, so a collision would be no evidence of a bug. Left alone with a
  comment saying so rather than pretending it still proves what it used to.

### What PB-058 did NOT settle — this is Joe's

The card carries a second question: **should the four Red List tiers
(`near-threatened`, `vulnerable`, `endangered`, `critically-endangered`) be
drawn for a five-year-old at all?** Not settled here, and nothing was built for
either answer.

Worth knowing before it is raised: **this run made it not urgent.** All four
tiers have zero shipped species, so they are in `NOT_BUILT_YET` and cannot be
drawn today regardless. The question only becomes live on the day someone
proposes modelling them. If the answer is "no", the four ids move from
`NOT_BUILT_YET` to a third list and the modelling is never commissioned; if
"yes", they leave `NOT_BUILT_YET` when the models land like any other
collection. Either way it is a list edit, not a design.

### A finding, recorded not fixed — partial collections can never complete

`completion()` divides by the **roster** size, not the shipped size. `home-pets`
(14 of 16) and `africa` (13 of 16) therefore **can never reach 100%**, can never
free their active slot, and can never be the completion that opens the next
album. With five buildable collections and four slots, a child who draws both
partial ones can end up unable to open the fifth ever.

This is not new and it was not caused by this run — it is exactly what **JT-030**
already asks Joe (*may a collection unlock with a hole in it?*). It is left
alone deliberately: changing what `completion` divides by is a cadence decision
with his ruling pending. Flagged here so the next manager does not rediscover it
as a bug.

## PB-055 — the album's load lag

Joe's card, verbatim: *"when opening the animals in the album there can be a
load lag. explore idea of copying the already loaded 3d models? check
computational demand"*.

### The finding that changes the question: there are no JPGs

Zero `.jpg` or `.jpeg` files in the repo. Album portraits have always been
**rendered from the 3D models at runtime** and encoded to a PNG data URL
(`album.ts`, `r.domElement.toDataURL('image/png')`). The card's premise is
inverted: **Joe's suggested idea was already the design.**

So there was no expensive option to weigh against a cheap one. What the
exploration actually found was that the album was doing the expensive half of
his idea and skipping the cheap half.

### The real cause

`createPortraitRenderer` built its **own** `GLTFLoader` and fetched the base-24
GLBs independently of the island — while `pets.preview`, the island's own cache,
was already wired onto the album as `AlbumWorld.preview` and already used by the
pop-out.

Consequences, all measured:

- opening the album on the base page could re-fetch **up to 24 GLBs, 3.26 MB**,
  that the island was already holding, plus a duplicate copy in GPU memory;
- those copies missed `wearFaceUVs`, the face-decal fix that only the shared
  prototype gets — harmless while everything is natural colours, a real bug the
  day anything is dressed. `main.ts` and `docs/BACKLOG.md` both already admitted
  this in comments;
- the album cached the **result**, where `pets.ts` caches the **in-flight
  promise**, so two overlapping requests for one species each did the whole job;
- nothing was prefetched, so every page turn paid its full cost at the moment of
  the turn.

### What shipped, and why it is the cheap fix

Three changes, all in `src/island/album.ts`.

1. **The portrait renderer borrows the island's models.** `shapeOf`'s GLB branch
   is now `preview(species)`. `createPortraitRenderer` takes `preview` as a
   parameter; the private `GLTFLoader` and the `flattenImported` import are
   deleted. This is Joe's idea, and it cost a parameter. It also removes a
   latent path divergence (`pets.ts` used `${base}pets/…`, the album a bare
   `pets/…`).

   `pets.preview` returns `(await prototype(species)).clone(true)` — a fresh
   clone, safe to reposition and add to the portrait scene, and **never
   disposed**, because a clone shares geometry and materials with every pet of
   that species including ones she already owns (brief §19). The existing
   `scene.remove(model)` and the absence of any `dispose` are preserved exactly.

2. **The cache holds the promise, not the result**, mirroring `pets.ts`. A second
   caller joins the first instead of repeating the work. Negative (`null`)
   entries are still cached as hard as hits — the roster has ~320 species and
   only ~98 can be drawn at all, so without that an album full of blank slots
   asks for the same two hundred impossible portraits on every open. A
   **rejected** promise is evicted so a later open retries.

3. **The next page is prefetched.** `turn()` warms page `at + 1` only, on
   `requestIdleCallback` where available and `setTimeout` otherwise,
   fire-and-forget and never able to reject. Only `at + 1` — prefetching every
   page is precisely what the paging commit `761d26a` removed, and the comment
   says so, so the next reader does not "improve" it back.

Nothing in the rendered result changed: same 192px, same `setPixelRatio(1)`,
same lights, same framing maths, same three-quarter rotation, same tone mapping.

### What was NOT built, and why

Recorded in the header of `createPortraitRenderer` so PB-055 is not
re-explored:

- **A build-time JPG or thumbnail pipeline.** ~320 new assets and a new pipeline
  for a problem three lines of reuse solve. `album.ts`'s own header already rules
  out pre-drawn art for a ~1,000-variant space: it would drift from the models
  the moment either changed.
- **Any offscreen or worker render-to-texture path.** None exists in the tree,
  and `toDataURL` is not the bottleneck the card describes.

### The honest remainder

The ~24 synchronous `toDataURL` PNG encodes on a full base page are main-thread
work independent of the network. The prefetch moves them **off the turn**; it
does not remove them. If a real device still janks, chunking the encodes or
`createImageBitmap` is the next lever. That is written into the code, not just
here.

### The tests are real, and were reverted to watch them fail

New file `tests/island/album-portraits.test.ts`, 11 tests. The two existing
album suites cannot reach this code at all — with no WebGL, `shoot` returns
before it ever asks for a model. So the new file stubs **the GPU only**: a
constructible `WebGLRenderer` that records the uuids in the scene at render
time, and a `GLTFLoader` that *would work*, then asserts it is never asked.
`world.preview` is a real function returning a real `THREE.Object3D`.
Assertions are on uuids, call counts and `img.src` — never on a mock having run.

Each change was reverted and the tests watched to fail:

- change 1 reverted → 8 of 11 failed: *"the island was never asked for the fox:
  expected undefined to be truthy"*, and *"expected 1 to be 24"*;
- change 2 reverted → exactly 1 failed: *"the second open must join the first:
  expected 2 to be 1"*;
- change 3 reverted → exactly 2 failed: *"expected +0 to be 1"* and *"expected []
  to have a length of 1"*.

`album.ts` was byte-compared against its pre-revert copy afterwards: identical.

## What I learned that is not in the code

- **A holding pen and a build gate look identical and are not.** `HELD_BACK`
  was one list doing one job; the moment it did two, "why is this id here" had
  no answer and "when does it come out" had two different ones. Splitting the
  list was worth more than the four lines it cost.
- **`HELD_BACK` gates the DRAW, not the DISPLAY.** This is the trap in the card's
  "fix is one line". A collection already in a save is never re-examined against
  it, and because `completion` divides by the roster size an unbuilt one is
  permanently incomplete, permanently active, and permanently holding a slot. A
  one-line fix would have left every existing player with the bug the card was
  filed about.
- **A test can go green by going vacuous.** Two of the Red List tests kept
  passing after the tiers became undrawable, because their loop bodies stopped
  running. Nothing flagged it. When a filter widens, grep the tests for the
  things it now excludes and check each one still executes.
- **`unlock.ts` cannot import `registry.ts`.** The registry reaches three.js
  through `collections/garden.ts` → `parts/assembled` → `parts/texture.ts`, and
  the unlock rules are deliberately pure. Any "just derive it at module load"
  instinct dies here — derive it in the test instead.
- **`pets.preview` is a clone and must never be disposed**, and it is the
  correct source for anything that wants a model: it is the only path that has
  had `wearFaceUVs` applied. Two features have now been built with a private
  `GLTFLoader` beside it. If a third needs a model, it takes the port.
- **"Explore the idea of X" is sometimes answered by "X is what it already
  does".** The exploration for PB-055 was worth more than any fix in it: the
  card described JPGs and a decode lag, and there are no JPGs. Measure the
  premise before costing the options.
