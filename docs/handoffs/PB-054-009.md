## PB-054 — `pettap.test.ts` flaked about one run in six

**Shipped: the rng is injected. No retry, no tolerance.**

`src/island/pets.ts` drew five numbers from `Math.random()`. They are now drawn
from an `Rng` threaded through `createPetField(base = '', rng = defaultRng)` —
the repo's ordinary convention (`src/core/rng.ts`), matching `deal.ts`,
`unlock.ts`, `opened.ts` and `collection.ts`. Production passes nothing and gets
`Math.random`, so pets wander exactly as varied as they always have, and nothing
in a save is seeded from it. All nineteen existing `createPetField()` callers
compile and behave unchanged; only `tests/island/pettap.test.ts` passes a seed.

### The mechanism, which is NOT what the card says it is

The card's diagnosis was half right and the wrong half is worth writing down.

Right: the randomness is real, it is in the product, and the test asserting on
it without controlling it was the defect.

**Wrong: it is not load-sensitive, and the degenerate push-out is not the
trigger.** It is a plain ~1-in-8 coin toss on the pet's opening goal, and it
fires identically on an idle machine. The sequence:

1. `sync` gives the new pet `goal: randomSpot(...)`. The test island is ONE hex
   (`pettap.test.ts:71`), so the goal is uniform in a 0.92-unit square about the
   origin, and the pet hatches at the origin. About 12% of the time the goal
   lands within the 0.12 "arrived" radius (`pets.ts:917`) — measured: 3 of the
   first 24 mulberry32 seeds.
2. The test then calls `setObstacles([{x:0,z:0,r:0.5}])`. That path sets
   `l.restFor = 0` for any pet whose goal the new obstacle covers
   (`pets.ts:885`) — and a goal that close to the origin always is.
3. Frame one therefore takes the *arrived* branch, runs the rest countdown
   straight through zero, and **draws a new goal** (`pets.ts:926`). The pet
   itself never moves, so `clearOf` uses its dead-centre branch and puts it at
   `(keep, 0)` — x = 0.6144, z = 0.
4. The test resets the position to `(0,0,0)` and replays the frame. But it reset
   only the POSITION; `goal` and `restFor` are pet state too, and frame one
   changed both. Frame two now walks toward the *new* goal and `clearOf` clamps
   along that direction instead. Different answer, nine-decimal assertion, fail.

The test's own comment — *"played twice from the same start, so the hop, the
random phase and the goal are all the same"* — was an assumption, not a fact.
The seed is what makes it true, and the comment now says so.

### The degenerate case at the obstacle centre — already understood, not papered over

The card asks that this not be hidden. It is not, and it did not need new work:
`clearOf` handles zero separation explicitly at `pets.ts:393` (`if (d < 1e-4)`,
push along +x), and `tests/island/pets.test.ts:206` already pins it — *"gets a
pet out of a keep-out it is standing dead in the middle of"*, asserting
non-negative clearance of BOTH of two overlapping keep-outs. So the geometry the
card compares to the sealing bug is covered, and I added nothing there rather
than duplicate it.

What the degenerate branch actually contributed to this flake is narrower than
the card supposed: it is not the *cause*, it is what makes the two frames
DISAGREE so loudly. Frame one's answer is `(keep, 0)` — a fixed direction that
has nothing to do with where the pet wanted to go — while frame two's is
`keep × unit(goal)`. Any two different goals would have diverged; the dead-centre
branch just guarantees the divergence is a large one.

### `governors.test.ts` — same load sensitivity? No. Nothing to fix.

The card says `governors.test.ts > leaves a wide corridor...` shows the same
sensitivity from the same cause. **It does not, and the same seam does not cover
it, because there is nothing to cover.** Measured:

- `tests/island/governors.test.ts` contains no `Math.random`, no `rng`, no
  `createPetField` — grep returns nothing. The file has no randomness at all.
- The named test (`governors.test.ts:533`) is pure arithmetic on `ceiling(pets)`
  and `floor(pets)` for a fixed list `[6, 8, 10, 20]`. There is no source of
  variation in it.
- 14 cold runs, concurrent with the pettap loop: **43 passed, 43 passed, ×14.**

If that test has ever flaked it is from a different cause, and there is no
evidence in this tree that it has.

### The two historical comments — left alone, deliberately

`pettap.test.ts:13` (*"or a tile offer, or a half-built plot resuming into a
sum"*) and `retype.test.ts:193` (*"tapping any socket called `askForLand`, which
resumes a standing plot"*) both narrate plot resumption, which has been
impossible since PB-050. Both are past-tense prose describing the fault that was
fixed, not claims about today's code. **Neither is touched.** The code was not
changed to match them and they were not deleted.

## PB-009 — a quarter of dead trunks flicker shadowless

**Shipped: the test was corrected. The product is right and renders unchanged.**

The card offered shadow-by-KIND or correct-the-test and did not decide. The
evidence decides it, and the answer is the test.

### VARY is ONE definition, not five copies

The card lists `egg.ts`, `fred.ts`, `juice.ts`, `pets.ts` and `world/props.ts`.
Measured: `VARY` is declared once, at `src/island/world/props.ts:535`, and is
imported by exactly one other file — `tests/island/shadow.test.ts`. The four
other files named do not reference it, do not carry a copy, and contain no
`(h >> n) % span` size arithmetic. The three sites that consume it are all in
`props.ts` (`:955` scatter, `:1080` water pieces, `:1213` tile features). **There
is no divergent copy to miss.**

### What is actually true, measured rather than repeated

Over 15,129 pieces, driving the real `hash()` from `mountains.ts:51` at the real
`props.ts:920` coordinates:

```
negative vary term      48.8%     (the card's figure, confirmed)
bare fitted height      0.252 .. 0.868   (not 0.560 .. 0.868)
dead trunks with no blob 24.5%    ("a quarter", confirmed)
live tree height        0.536 .. 1.460
live trees with no blob  0.0%
```

So the reported behaviour is real. But three things follow that the card did not
have:

1. **They do not flicker.** A piece's size is a pure function of its axial hash,
   so a given trunk is that size for the life of the save. What varies is WHICH
   trunk, never one trunk over time.
2. **`shadowUnder` is a rule about SIZE, not kind** — deliberately, and the
   header at `props.ts:601-618` argues it at length: a height-only or kind-only
   rule was rejected because the same model would gain and lose its shadow. The
   smallest dead trunk is **0.252 tall and 0.081 across** — SHORTER than the reed
   at 0.322 and NARROWER than the tuft at 0.260, both of which the threshold
   excludes on purpose. Shadowing it by kind would put a blob on the smallest
   thing on the tile while the taller reed beside it has none. That is less
   consistent on screen, not more.
3. **Shadow-by-kind would change what an existing island renders**, adding blobs
   to Juno's island under her, and I cannot show the current render is broken.
   The standing constraint says that is a regression, not a fix.

### The real defect: `min` is not a floor, and only the ceiling had a helper

`varyMax` existed (`props.ts:566`) precisely because a ceiling copied by hand
goes stale. Nothing did the same for the floor, so four assertions used
`VARY.*.min` as if it were one. It is not: the term is `-(span-1) .. span-1`, so
the true floor is `min - (span - 1) / 100`.

`shadow.test.ts:306` asserted `FITS.bare[1] * VARY.cover.min > SHADOW_MIN_HEIGHT`
and passed at 0.560 — certifying that **every** dead trunk earns a blob. The true
floor is 0.252 and a quarter of them do not. That assertion was false about the
product, and it was the assertion the shadow threshold's lower edge was justified
against. That is the defect.

### The change

- **`props.ts`** — added `varyMin`, the exact counterpart of `varyMax`, with the
  measured numbers and the PB-009 autopsy in its doc. Added a note on the
  `VARY.cover` entry, which is the one that sizes dead trunks and previously
  carried no warning at all (the warning lived under `tree`).
- **`shadow.test.ts`** — split the false assertion in two. *"is cleared by the
  shortest live tree there can ever be"* keeps the true half on the true floor
  (0.536 > 0.4). *"is NOT cleared by the smallest dead trunk, and that is correct
  — PB-009"* asserts the truth from both sides: the smallest fails both arms, it
  is smaller than the reed and the tuft the rule excludes on purpose, and a trunk
  at its nominal fit and every larger roll still earns its blob. Also moved the
  two `VARY.feature.min` uses at `:318-319` onto `varyMin` — same false idiom,
  still true at the real floor (0.315 and 0.536 against 0.29).

**No render changes. `>>` is untouched, exactly as the card demands.**

### What needs Joe

Purely a taste question, and it does not block anything. **Is a 0.25-unit dead
trunk with no blob acceptable, or does he want all dead trunks shadowed?** The
geometry says the current behaviour is consistent; only his eye can say whether
it looks it. If he wants them shadowed, that is shadow-by-KIND, it changes what
her existing island renders, and it needs his ruling first because of that.

## The flake evidence, which is the deliverable

A single green run proves nothing about a flake, so it was measured the way the
original diagnosis was — cold runs of the file on its own.

**Before, unseeded — 1 failure in 14 cold runs:**

```
RUN 1..5   pass   Tests  33 passed (33)
RUN 6      FAIL   Tests  1 failed | 32 passed (33)
   FAIL  pettap.test.ts > does NOT let the camera into the keep-out or the blob
   AssertionError: expected 0.39495121645000575 to be close to 0.614399995803833,
   received difference is 0.21944877935382723, but expected 5e-10
RUN 7..14  pass   Tests  33 passed (33)

RESULT: 1 failure in 14 cold runs
```

(An earlier 9-run pass of the same loop also failed on run 6, same assertion,
same numbers — so it reproduced twice before the fix.)

**After, seeded — 0 failures in 16 cold runs, runs 11 to 13 taken while the full
2,739-test suite was running concurrently:**

```
RUN 1..16  pass   Tests  33 passed (33)

RESULT: 0 failures in 16 cold runs
```

**And the assertion still has teeth.** The discipline is to break the fix and
watch the test fail. Setting `SEED = 11` — one of the three seeds in the first
twenty-four that puts the opening goal inside the arrived radius — reproduces the
original failure **deterministically**, against the same expected value:

```
FAIL  pettap.test.ts > does NOT let the camera into the keep-out or the blob
AssertionError: expected 0.133104845042024 to be close to 0.614399995803833
```

That is the proof that the seed controls the mechanism claimed above, and that
the test was not quietly neutered. Seeds 11, 14 and 18 all reproduce it; 7 is
shipped because it puts the goal 0.598 away, the furthest of the twenty-four and
five times the arrived radius.

## What I learned that is not in the code

Four things, the first two worth promoting into `docs/HANDOFF.md` §6.

- **Resetting a pet's position is not resetting the pet.** `goal`, `restFor`,
  `phase` and `stuckFor` all live in the `live` map and all survive a write to
  `root.position`. Any test that "replays a frame" by setting the position back
  is comparing two different simulations unless it also controls the rng. This
  is the whole of PB-054 and it will recur the moment someone writes another
  replay-a-frame test.
- **`setObstacles` mutates pets, it does not only publish geometry.** It zeroes
  `restFor` for every pet whose goal the new obstacle covers (`pets.ts:885`), so
  calling it in a test arms a goal re-draw on the very next frame. It reads like
  a pure setter and is not one.
- **A one-hex test island makes rare things common.** `pettap.test.ts` runs on
  `{tiles: new Map([['0,0','grass']])}`, so every `randomSpot` draw lands in the
  same hex as the pet and the "goal is where I already am" case goes from
  negligible to about one in eight. Convenient for reproducing; a trap when
  reading a probability off a test.
- **`min` in a `{min, span}` pair in this repo is a CENTRE, not a floor**, wherever
  the term is `(h >> n) % span` on a signed shift. `varyMin` now exists so this
  is arithmetic rather than folklore, but the same idiom may appear elsewhere:
  audit any `.min` used as a lower bound before trusting it.
